Architecture

Definitions ≠ runtime state

Unity assets define stable content; mutable inventory/save state lives in an engine-agnostic C# object. That reduces accidental asset mutation and makes persistence easier to test or move behind another authority boundary.

[CreateAssetMenu]
public sealed class ItemDefinition : ScriptableObject
{
  [SerializeField] string stableId;
  public string StableId => stableId;
}

public sealed class InventoryState
{
  readonly Dictionary<string,int> quantities = new();
}

Tooling

Fail invalid content before runtime

A small Unity editor validator searches authored definitions for duplicate IDs and missing display names. The broader principle is that repeatable content rules belong in tooling rather than memory or review checklists.

[MenuItem("Tools/.../Validate")]
public static void ValidateAll()
{
  var duplicates = assets
    .GroupBy(x => x.StableId)
    .Where(g => g.Count() > 1);
}

Testing

Keep rules testable without a scene

The runtime state has no UnityEngine dependency, so stack limits and transactional removal can be covered with ordinary NUnit tests rather than booting a scene or relying on manual playtesting.

[Test]
public void Add_RespectsMaxStack()
{
  var state = new InventoryState();
  Assert.That(state.Add("wood", 8, 10), Is.EqualTo(8));
  Assert.That(state.Add("wood", 5, 10), Is.EqualTo(2));
}

Read scope & tradeoffs

Tradeoffs I would expect to discuss in an interview

  • String IDs: save stability and decoupling versus lookup/migration overhead.
  • Dictionary runtime state: simple direct lookup versus indexed/data-oriented storage for very large or hot-path systems.
  • Editor validation: excellent for authoring errors, insufficient for untrusted/network data.
  • ScriptableObjects: strong authoring primitive, poor place for mutable player state.
  • No fake networking sample: authority, prediction and replication depend heavily on the networking stack; a toy abstraction would signal less than a clear boundary.
